# 永続インデックスの設計（#16）

Linux の 2 回目以降の走査を速くするための設計。Issue #16 が求める第一段階の設計文書。

## まず実測: 既存の実装は目的と正反対に働いている

`hyperdu-core/src/incremental.rs` に sled ベースの永続インデックスが既にあり、CLI から
`--incremental-db` / `--compute-delta` / `--update-snapshot` で使える。**これが速いかどうかを
測ったところ、遅かった。**

`/usr/share`（21,815 ファイル、WSL2 / ext4 / kernel 6.18、warm、3 回の最小値）:

| 操作 | 時間 | メタデータ syscall |
|---|---|---|
| 通常スキャン | **19 ms** | 21,826 |
| `--compute-delta` | **213 ms（11.2 倍遅い）** | **54,192（2.5 倍多い）** |
| `--update-snapshot` | 259 ms（13.6 倍遅い） | — |
| インデックス構築（初回） | 410 ms | — |

インデックスのサイズは **12 MB**。1 ファイルあたり約 550 バイトで、19 ms で終わる走査のために
これを維持していることになる。

### なぜ遅いのか

`compute_delta` は変更を検出するために**ツリー全体を歩く**（`incremental.rs:96-154`）。

```rust
let rd = std::fs::read_dir(dir)?;          // 走査と同じ
let Ok(md) = ent.metadata() else { ... };  // 走査と同じ stat
if let Some(v) = db.get(&key) { ... }      // その上に DB 参照が増える
```

つまり「走査を避けるためのインデックス」が、走査に DB 参照と JSON デコードを足したものになっている。
syscall が 2.5 倍なのは、`read_dir` + `metadata()` の組が本体の `getdents64` + `statx` より
高コストで、ディレクトリ自身にも stat をかけるため。

**これは実装の粗さではなく、構造の問題である。** 木を歩いて変更を検出する設計は、
どうやっても走査より速くならない。走査とはその歩行そのものだからである。

### 付随する問題

- **集計値を持っていない。** `PathSnapshot` はファイル単位の `{path, mtime, size, dev, ino}` だけで、
  ディレクトリごとの合計がない。「このディレクトリは何 GB か」に答えるには結局歩く必要がある
- **キーがフルパス文字列。** 12 MB のうち相当部分がパスの重複。`scan_prefix("/a")` は `/ab` にも当たる
- **1 ファイルごとに `serde_json`。** エンコード・デコードのコストが全ファイルに乗る
- **`watch` がどこにも繋がっていない。** `incremental.rs:177` の inotify ラッパは CLI から
  イベントを表示するだけで、DB を更新しない
- **テストがない**

## 唯一の道: 歩かないこと

2 回目を速くする方法は「変化した部分だけ更新する」ではなく、**そもそも歩かない**ことしかない。
そのためには、何が変わったかをカーネルに教えてもらう必要がある。

Issue #16 が指摘するとおり、ディレクトリの mtime では足りない。**既存ファイルへの書き込みは
親ディレクトリの mtime を変えない。** ログ、VM イメージ、DB の成長という「容量がどこへ消えたか」の
典型例がまさにこれで、走査を省く判断材料にならない。

inotify は `IN_MODIFY` / `IN_CLOSE_WRITE` / `IN_CREATE` / `IN_DELETE` / `IN_MOVED_*` を
ディレクトリ単位の watch で非特権のまま受け取れる。fanotify の `FAN_MARK_FILESYSTEM` は
`CAP_SYS_ADMIN` を要するので採らない。

### 必然的に常駐プロセスが要る

inotify のイベントはプロセスが動いている間しか届かない。プロセスが落ちていた間の変更は
取りこぼす。したがって以下は避けられない。

- 常駐プロセスの起動・停止・自動起動の設計
- **常駐していなかった区間をどう扱うか**（後述の鮮度保証）
- watch 数の上限（`fs.inotify.max_user_watches`）への対処

**これは技術判断ではなく製品判断である。** 「ディスク使用量を見るために常駐プロセスを入れるか」
という問いに、この文書は答えを持たない。

## 提案する設計

### インデックスの形式

ファイル単位ではなく**ディレクトリ単位の集計**を持つ。これが既存実装との決定的な違い。

| キー | 値 |
|---|---|
| ディレクトリの inode（`(dev, ino)`、16 バイト） | `{ own_bytes, own_files, subtree_bytes, subtree_files, generation, state }` |

- **キーを inode にする**のは、パス文字列の重複を避けるためと、`mv` でパスが変わっても
  同一性を保てるため。パスは別テーブルに inode → 名前 + 親 inode で持つ
- **`subtree_*` を持つ**ので、ルートの 1 件を読むだけで総量が出る。ここが「走査しない」の実体
- **`generation`** は更新の世代番号。祖先へ差分を伝播するときに二重加算を防ぐ
- **`state`** は `Fresh` / `Stale` / `Unknown` の 3 値（後述）

ファイル単位の情報は**持たない**。1 ファイルあたり 550 バイトは、19 ms で終わる走査に対して
釣り合わない。ファイル単位が要るのは「どのファイルが大きいか」を答えるときだが、それは
ディレクトリを絞り込んだ後に、そのディレクトリだけを走査すればよい。

### 鮮度保証の 3 状態

利用者に嘘をつかないために、状態を隠さず持つ。

| 状態 | 意味 | 表示 |
|---|---|---|
| `Fresh` | 常駐プロセスが継続的に watch していた区間で、イベントを取りこぼしていない | そのまま表示 |
| `Stale` | watch していなかった、または `IN_Q_OVERFLOW` が起きた | **値を出すが「古い可能性」と明示** |
| `Unknown` | 一度も走査していない | 走査を促す |

`IN_Q_OVERFLOW` は該当サブツリーを `Stale` に落とす。**黙ってフル再走査に落ちるのではなく、
状態を見せてから利用者に選ばせる。** 「速いと思って使ったら実は毎回フル走査だった」というのが
最も避けたい失敗である。

### watch 数の上限

`fs.inotify.max_user_watches` はディストリビューションによって 8,192〜数十万と幅がある。
上限に当たったサブツリーは `Stale` に落とし、**そのサブツリーだけ**走査対象に戻す。

上限を超えるツリーで全体を諦めるのではなく、watch できた範囲は `Fresh` のまま使う。
どこまで watch できているかは検査コマンドで見せる。

### 複数ルート

インデックスはルートごとに独立させる。ルート間でサブツリーを共有しない（bind mount や
ハードリンクで論理的に重なることはあるが、集計は独立に持つ）。

## 判断が必要な点

Issue #16 が挙げたとおり、以下は着手前に決める必要がある。

1. **常駐プロセスを持つか。** 持たないなら、この機能は原理的に成立しない
   （歩かずに変更を知る手段が他にない）
2. **インデックスの保存場所。** `$XDG_STATE_HOME/hyperdu/` が妥当だが、ルートごとに
   置くか単一 DB にまとめるか
3. **鮮度の保証レベル。** 上記の 3 状態で足りるか、`Stale` をどこまで細かく持つか

## 既存実装の扱い

**現行の `--incremental-db` は削除を推奨する。**

11 倍遅く、2.5 倍の syscall を発行し、12 MB を消費して、得られるものが「追加・変更・削除の件数」
だけである。同じ情報は `find -newer` で足りる。残しておくと「インデックスがあるのに速くない」
という誤った印象を与える。

削除するなら以下が対象になる。

- `hyperdu-core/src/incremental.rs`（200 行）
- `hyperdu-cli/src/main.rs` の `--incremental-db` / `--compute-delta` / `--update-snapshot` / `--watch`
- `sled` への依存（`watch` を残すなら `notify` は維持）
- `scripts/bench.sh:95-96` の `incr-update` / `incr-delta` ケース
- `packaging/man/hyperdu.1:104-105`
- `README.md:146`

## 段階

1. **この文書の判断事項を決める**（製品判断）
2. 決まったら、まず**インデックスの読み書きと集計**だけを作り、更新は手動コマンドで行う。
   この時点で「ルート 1 件の読み出しで総量が出る」ことを実測する
3. inotify 連携と常駐プロセスは次段階。`Fresh` / `Stale` の遷移が正しいことを、
   イベントを人工的に落とすテストで確かめてから繋ぐ

---

**計測環境**: WSL2（kernel 6.18、ext4、16 vCPU）、`/usr/share` 21,815 ファイル、warm、3 回の最小値。
Issue #16 が定める正の環境は EC2 t3.large / xfs だが、AWS 認証が期限切れのため代替した。
既存実装が 11 倍遅いという結論は倍率が大きく、環境差で覆るものではない。
